## r.1 拼湊開源套件的真正代價

**原始想法**：常見的 RAG 做法是把開源套件湊起來，造成大量 code duplication；那些把它們串起來的 glue layer 本身也帶來複雜度。

**修正後**：問題的核心不是「程式碼重複」，而是**資料與權限在多個系統之間同步**：

- **資料重複**：同一份文件分別存在向量 DB、搜尋引擎、metadata DB 與框架的 document store。
- **一致性沒有交易保護**：新增、修改、刪除要在每個系統都成功，但沒有跨系統的交易，失敗時只能靠補救邏輯。
- **ACL 重複實作**：每個儲存各自過濾權限，只要漏掉一處就會洩漏。
- **glue code 的複雜度**確實存在：各元件的介面、設定、版本相依。這一點成立，但它是上面三項的結果，不是根源。

## r.2 RAG 的檢索是資料庫問題

**原始想法**：RAG 本質上是延伸資料庫的問題，應該以 DB 為中心來設計，所以從零開始做。

**修正後**：限定在**檢索**這一半。索引、查詢、權限、交易、可重建，都是資料庫問題；生成則不是。

在 levinrag 裡的具體體現：

- 單一嵌入式 Datalevin：文件、章節、chunk、全文索引、向量、連結圖、ACL 都在同一個 DB（`index.dtlv`）。
- 語料目錄是唯一的資料來源；`index.dtlv` 隨時可以從語料完整重建（`bb reindex`），不影響帳號（另存在 `app.dtlv`）。
- 一份文件的所有衍生資料在**同一個交易**中寫入或更新。

## r.3 類比 ELT 的 T：放在寫入端

**原始想法**：一個查詢同時處理 BM25、向量、graph、ACL 等多種索引，把這件事推進 DB，就像 EL"T" 裡的 T。

**修正**：這與實作不符，不能照原樣寫。實際情況是：

- lexical（`fulltext`）與 semantic（`vec-neighbors`）是**兩個獨立的 DB 查詢**；
- ACL 不是在查詢中 join，而是先多撈一些，再用「可讀文件 id 集合」過濾。Datalog join 在 100k chunks 下太慢，是實測得出的結論；
- RRF 融合、graph 擴展、rerank、context 打包都在應用層的 pipeline；
- embedding 由應用程式呼叫模型（Path B），不是 DB 內建功能。

**可以成立的說法**：ELT 的類比適用於**寫入端**。原始文件載入之後，所有衍生資料在同一個 DB、同一個交易中「就地轉換」完成：

- 解析出章節樹與 chunk；
- 全文索引；
- 向量；
- ACL 的 effective groups（在寫入時就算好）；
- 連結圖。

查詢端則是**對同一個儲存的幾個查詢，由一條可觀察的 pipeline 串起來**，不是單一查詢。

## r.4（新增）可觀察性

初版規格 §1.1 的核心目標之一：每一次查詢都能看到各通道撈到什麼、排第幾、rerank 之後怎麼變化。

- Debug 面板與 trace 逐一列出每個候選在每個階段的名次與分數；
- 這在拼湊式架構中很難做到，因為資料分散在多個系統，每個元件各自回傳結果；
- 這是本專案最名副其實、也最有說服力的特點：它本身就是學習與調校 RAG 的工具。

## r.5（新增）誠實寫出代價

有寫代價的 rationale 比較可信：

- **規模上限**：約 5,000 份文件或 100k chunks（嵌入式 DB，單一 process，不做水平擴展）；
- **Datalevin 的 bus factor**：維護者集中。以 Retriever protocol 隔離，index 也可以重建；
- **功能廣度**不如 LangChain、LlamaIndex、Haystack 這類框架：沒有 PDF 解析、沒有 agent、沒有多輪對話。
